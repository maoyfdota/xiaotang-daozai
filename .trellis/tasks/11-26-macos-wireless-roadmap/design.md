# 无线设备首期设计草案

范围基于 prd.md。已获准在当前分支实施；首期只做蓝牙，2.4G 后续安排。

## 现有能力与拟改动位置

| 现有位置 | 现状 | 拟调整 |
| --- | --- | --- |
| src/bt.rs | 地址身份、连接状态、可选电量、状态和观测序号 | 添加电量来源、读取时刻和有效性，不重写全部设备模型 |
| src/bt/macos.rs | IOBluetooth 配对枚举／控制，system_profiler 聚合电量 | 明确来源元数据和缓存限制；先调查安装后权限状态差异，新增数据源须通过能力验证 |
| src/bt/management.rs | 有界工作线程、控制请求关联、实际状态确认 | 保留并复用；读取／展示增强不改变单设备操作语义 |
| src/bluetooth_ui.rs | 设备列表、电量、操作按钮和设置回退 | 电量环总览、详情、常驻设置和状态说明 |

| src/main.rs 及 Mac 打包入口 | Mac 外壳、授权入口和应用交付 | 权限异常调查涉及此处；当前规划不重置权限、不替换运行包 |

## 1. 先稳定数据和身份

推荐保留 Device 与管理服务接口，新增小型“电量观测”结构或等效字段，覆盖：

- 数值：可选 0–100；不支持／失败不使用 0 作为占位。
- 来源：现有系统报告，未来经验证的来源；来源可读性与可靠性分别表达。
- 读取时间：本次查询完成时间；仅当来源给出设备采样时间时才另存采样时间。
- 有效性：新有效值、已过期的最后值、未知、失败；过期时间按来源制定并测试，不随 UI 帧刷新。
- 连接代次／观测序号：重连之前的缓存不成为新连接后的有效读数。

UI 中“最近读取”不能写成“设备刚更新”。数据源自身缓存无法确定新鲜度时，明确显示有限时效，不借应用轮询时间伪造设备更新时间。

设备身份继续以当前已验证的稳定地址为主。其他系统标识与地址关联必须有确切依据；不因名称相同、图标相同或电量相近而合并。无法可靠关联时宁可记录为未关联来源，不控制另一台设备。

多个来源冲突时按明确的来源优先级和时效规则选择；过期缓存不覆盖新有效值。首期只有一个可靠来源时先完成统一表示，不为“多来源”目标添加未经验证的读数。

## 2. 权限状态差异的调查关卡

已知事实：此前连接／断开功能实机可用，用户确认音频正常；最终安装包替换后曾出现应用报告需权限、系统开关已开启的情况，尚无最终原因结论。

进入实现后的调查顺序：

1. 核对实际进程路径、包标识、使用说明字段和启动来源，区分开发二进制与最终应用。
2. 记录 CoreBluetooth 授权状态、IOBluetooth 枚举结果及界面错误映射。
3. 核对授权请求时机、应用替换前后行为及错误状态传播。
4. 将可复现原因写成针对性修复和回归；无法复现时保留记录，不擅自归因于未签名、缓存或系统问题。

不自动执行 TCC 重置；不把诊断命令作为绕过权限的通道。资料及日志须限制设备地址等识别信息的外露。

## 3. 页面与详情

- 总览优先展示已连接设备；无有效电量仍保留设备入口，使用明确的未知状态。
- 电量环配合百分比和名称，不只靠颜色区分；详情保留受支持的连接／断开、刷新和设置回退。
- 未连接设备仍可查看和连接，可用分组减少总览拥挤。
- 长名称、同名设备、长列表和深浅色主题均需覆盖。
- 读取失败允许保留上次已知数值，但显式标为过期／读取失败，停止依赖该值产生事件。
- 键盘断开确认、操作防重、真实状态确认和超时恢复维持现有合同。
- 页面显示名可改为“无线设备”；保存 ID 9 和设置 ID 15。未来性能页分配独立 ID，不能直接复制主线 9=性能／10=无线设备。

## 4. 常驻策略

建议默认关闭；开启后提供自动／自选和两种显示样式：

- 自动：从已连接且具有有效电量的设备中取最多两台，电量从低到高；相同电量使用稳定身份顺序，避免轮询抖动。
- 自选：保存最多两台设备 ID 和用户顺序。断开／移除不丢失选择，也不自动换成别的设备；断开的槽暂不显示，重新连接后恢复。
- 已连接但电量暂不可用的自选设备可显示未知占位，不能显示旧值为实时值。
- 两种样式：环＋数字、仅环；点击可进入对应设备详情。
- 没有可展示设备时收回空间；与原有时钟、天气等组件共同居中和排序。
- 在当前 Mac 右侧停靠布局及既有缩放下实现，后续底部停靠阶段复用。
- 组件显示、页面显隐和提醒开关分别保存。隐藏页面不隐式关闭提醒；关闭常驻不影响管理。
- 旧常驻顺序迁移保留原槽相对顺序，只附加新槽；验证通过前不重排用户设置。

## 5. 提醒规则

继续使用“收到观测 → 判断资格 → 排队 → 展示前复核 → 实际展示确认 → 持久化”的流程。

| 事件 | 资格与去重 |
| --- | --- |
| 连接变化 | 保留当前独立开关；首次快照建立基线，读取失败不伪造断开 |
| 低电量 | 新有效读数 ≤20% 每轮一次；有效 >20% 才恢复资格；重连／改名／重启不重复 |

实机探查未得到可关联到蓝牙地址的外设充电状态，首期不添加充电字段、占位提示、动画、提醒和设置。未来若有明确数据源，开始充电和充满也必须由可信的状态变化触发，不能由电量上升或 100% 推断。

总提醒开关、排队后断开、来源过期、读取失败、重启恢复都需覆盖。

## 6. 数据源扩展与 2.4G 的验证关卡

规划本身不承诺特定 Mac API 可以提供所有设备的电量或充电状态。新增原生源前应核对官方文档、最低系统可用性和实际设备证据。

蓝牙后续候选：受支持的 BLE 电量／充电特征、系统可读的 HID 信息。只有身份关联、读取方式、超时／取消、权限和观测可靠性全部明确后才接入；不因标准存在就假设每台设备都实现。

2.4G 已确认后置，届时按独立子阶段处理：

1. 取得用户目标设备／接收器型号及 VID/PID 等识别证据。
2. 先验证接收器识别，再分别证明外设连接状态、电量和充电状态可读取。
3. 插入接收器只能表示接收器存在，不能代表鼠标／键盘在线。
4. 必要协议逻辑以本体代码实现并限制支持范围；不接入已排除的兼容包插件。
5. 有协议和实机证据才承诺电量／提醒；否则交付识别与限制说明。

## 7. 验证与交付

定向验证：身份合并、来源优先级、时间／缓存、状态转换、去重、配置迁移、常驻排序和页面路由。UI 验证覆盖未知／过期、长列表、两种主题、既有缩放和透明区域点击。

后续实机检查只针对新能力与权限问题，不在规划期间连接／断开或播放音频。已有音频验收仍有效；若实现改动影响控制或音频路径，再安排对应回归。硬件样本不足时记录“未覆盖”，不能以单元测试替代。

保留 Apple Silicon 和现有 macOS 11 部署目标；新接口逐项核对可用版本，部署目标不等于已经实测旧系统。数据目录及隔离测试约定继续沿用。

分支集成和应用替换遵守 prd.md 的暂停合并约束，不能用默认工作流自行覆盖用户要求。
